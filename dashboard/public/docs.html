1. Architektur

Das Dashboard ist ein schlanker, eigenständiger Bun-HTTP-Server ohne externe Abhängigkeiten. Es liest ausschließlich — schreibt nie in NanoClaw-Datenbanken oder Konfigurationsdateien.

Server (dashboard/server.ts)

Bun-basierter HTTP-Server auf Port 3100. Beim Aufruf von /api/data wird buildSnapshot() ausgeführt — alle Datenquellen werden parallel abgefragt und als ein JSON-Objekt zurückgegeben.

RouteFunktion
GET /Liefert public/index.html
GET /api/dataVollständiger Snapshot als JSON
GET /api/logs/historyLetzte 500 Log-Zeilen (Main + Error Log gemergt)
GET /api/logs/streamServer-Sent Events — Live-Log-Stream (Polling alle 2 s)
GET /insights/latestAktuellster Claude Insights HTML-Report
GET /docsDiese Dokumentationsseite

Frontend (public/index.html)

Reines HTML + Inline-JavaScript ohne Framework. load() holt /api/data und übergibt das JSON-Objekt an die render*()-Funktionen der einzelnen Tabs.

Der Live-Log-Stream wird als Server-Sent Events aufgebaut, sobald der Log-Tab erstmals geöffnet wird.

Datenfluss beim Seitenaufruf

Browser → GET /api/data
  └─ buildSnapshot()
       ├─ openCentral()          → data/v2.db (readonly SQLite)
       ├─ collectContainers()    → Docker-Socket /var/run/docker.sock
       ├─ collectDisk()          → df -Pk /data
       ├─ collectTailscale()     → Tailscale-Socket
       ├─ collectSnapUpdates()   → Snapd-Socket
       ├─ collectLogMetrics()    → tail -n 8000 logs/nanoclaw.error.log
       ├─ collectRateLimitMetrics() → *.jsonl aus v2-sessions + ~/.claude/projects
       ├─ collectTokenMetrics()  → dieselben *.jsonl
       ├─ collectSessionData()   → inbound.db + outbound.db pro Session
       ├─ collectAgentDetail()   → data/v2.db (JOIN über agent_groups, wirings)
       └─ System-Metriken        → /host/proc/* (gemountet vom Host)

2. System-Metriken

Alle System-Metriken werden aus dem Host-Dateisystem gelesen, das im Dashboard-Container als Read-only-Bind-Mount unter /host/proc und /host/etc liegt. Ratewerte (CPU, Disk I/O, Netzwerk) werden durch Delta-Vergleich zweier aufeinanderfolgender Abfragen berechnet — beim ersten Aufruf nach dem Serverstart sind diese Werte noch 0.

CPU

Quelle

/host/proc/stat — enthält kumulierte Jiffies pro CPU und Kern seit Boot.

Berechnung

// Vereinfacht aus collectCpu() in server.ts
Δtotal = Σ(cur) - Σ(prev)          // Differenz aller Zähler
Δidle  = (cur.idle + cur.iowait) - (prev.idle + prev.iowait)
CPU%   = (Δtotal - Δidle) / Δtotal * 100

Die Funktion merkt sich den letzten Snapshot in prevCpu (Modul-Variable). Bei jedem API-Aufruf wird der neue Snapshot gelesen, die Differenz gebildet und prevCpu überschrieben. So ergibt sich ein Durchschnitt über das Intervall zwischen zwei API-Aufrufen.

Felder

  • overall — Gesamtauslastung aller Kerne in %
  • cores[] — Auslastung pro Kern in % (Array)
  • count — Anzahl logischer Kerne
  • ready — false beim ersten Aufruf (kein Vergleichs-Snapshot vorhanden)

Nützlich für

Erkennen von CPU-Engpässen durch parallele Agenten-Container. Ein hoher Wert bei einzelnen Kernen zeigt, dass Bun/Node single-threaded arbeitet und ein Container-Limit sinnvoll wäre.

Arbeitsspeicher

Quelle

/host/proc/meminfo — alle Zeilen werden als Key: Wert kB geparst.

Berechnung

used = MemTotal - MemAvailable   // Linux-Konvention: Available = freier + reclaimable Cache
usedPct = used / MemTotal * 100
swapUsed = SwapTotal - SwapFree
swapPct  = swapUsed / SwapTotal * 100

Es wird MemAvailable statt MemFree verwendet — das ist der korrekte „tatsächlich verfügbare" Wert (inkl. reclaimable Page-Cache und Slab).

Felder

  • total / avail / used — in Bytes
  • usedPct — Auslastung in %
  • buffers / cached — Kernel-Buffer-Cache
  • swapTotal / swapFree / swapUsed / swapPct

Nützlich für

Erkennen von Speicherengpässen bei vielen gleichzeitig laufenden Agent-Containern. Swap-Nutzung zeigt an, dass der Host unter Speicherdruck gerät — Container-Start-Latenz und I/O-Wartezeiten steigen dann stark an.

Disk

Disk-Nutzung — df -Pk /data

Misst Belegung des /data-Volumes (Session-DBs, Logs, Insights). Gibt filesystem, total, used, available, usePct zurück.

Nützlich für

Warnung vor vollem Disk — Session-DBs und JSONL-Historiendateien wachsen kontinuierlich. Bei >90 % wird ein Alert ausgelöst.

Disk-I/O-Raten — /host/proc/diskstats

Kumulierte Sektoren pro Gerät (512 Byte/Sektor). Delta zwischen zwei Abfragen ergibt Bytes/s. Partitionen (endet auf Ziffer) und Loop/RAM-Geräte werden übersprungen.

Felder

  • readRate / writeRate — Bytes/s
  • readBytes / writeBytes — kumuliert seit Boot

Netzwerk

Quelle

/host/proc/net/dev — kumulierte RX/TX-Bytes und -Pakete pro Netzwerk-Interface.

Berechnung

Gleiche Delta-Logik wie Disk I/O. Bei Zähler-Überlauf (counter wrap) wird Math.max(0, delta) verwendet, um negative Werte zu verhindern.

Felder pro Interface

  • rxRate / txRate — Bytes/s
  • rxBytes / txBytes / rxPackets / txPackets — kumuliert

Nützlich für

Erkennen von unerwarteten Netzwerk-Peaks (z. B. viele parallele API-Calls der Agenten) oder ob Tailscale-Traffic über Relay statt direkt fließt.

OS / Uptime / Load

Uptime — /host/proc/uptime

Erste Zahl = Sekunden seit Boot. Wird als Xd Yh Zm formatiert.

Load Average — /host/proc/loadavg

load1 / load5 / load15 = gleitender Mittelwert der CPU-Warteschlange über 1, 5, 15 Minuten. runningProcs / totalProcs = aktuell laufende vs. alle Prozesse.

Alert: load1 > CPU-Kerne × 1,5 = kritisch.

OS-Info — /host/etc/os-release

Liefert NAME, VERSION_ID, PRETTY_NAME u. a. aus dem Host-Betriebssystem.

3. Infrastruktur-Metriken

Docker

Alle Docker-Abfragen gehen über den Unix-Socket /var/run/docker.sock via HTTP. Timeout: 5 s. Ist der Socket nicht erreichbar, werden leere Werte zurückgegeben.
DatenquelleHTTP-EndpunktInhalt
Container-ListeGET /containers/json?all=1Alle Container inkl. gestoppter. Feld isNanoclaw = Label nanoclaw-install gesetzt.
Container-StatsGET /containers/{id}/stats?stream=falseCPU %: Delta cpu_usage vs. precpu_stats (ein Einzel-Sample). Mem: usage - cache.
ImagesGET /images/jsonSortiert nach Erstellungsdatum, max. 40 Einträge.
NetworksGET /networksName, Driver, Scope, Container-Anzahl.

Container CPU%-Berechnung

cpuDelta = cpu_usage.total_usage   - precpu_usage.total_usage
sysDelta = system_cpu_usage        - precpu_system_cpu_usage
cpuPct   = (cpuDelta / sysDelta) * onlineCPUs * 100

Docker liefert bei stream=false genau zwei Snapshots — cpu_stats und precpu_stats. Das ergibt eine Momentaufnahme über ein sehr kurzes Intervall (oft < 100 ms), nicht einen gleitenden Mittelwert.

Tailscale

Quelle

/var/run/tailscale/tailscaled.sock — Tailscale Local API, Endpunkt /localapi/v0/status. Timeout: 3 s.

Felder (Self)

  • backend — Soll "Running" sein. Alles andere löst einen Alert aus.
  • hostname / ips — Tailscale-Hostname und -IP(s)
  • relay — aktueller DERP-Relay-Server. Leer = direkte Verbindung.
  • keyExpiry — Ablaufzeit des Auth-Keys. Alert bei < 14 Tagen.
  • rxBytes / txBytes — Datenverkehr über Tailscale

Felder (Peers)

Dieselben Felder plus online, lastSeen, lastHandshake, exitNode, active, tags.

Nützlich für

Prüfen ob der Host erreichbar ist, welche Peers verbunden sind, und ob Verbindungen über DERP-Relay laufen (höhere Latenz) statt direkt P2P.

Paket-Updates

APT — /host/update-notifier/updates-available

Ubuntu/Debian schreibt hier einen Kurzbericht nach jedem apt update. Beispielinhalt:

12 updates can be applied immediately.
3 of these updates are security updates.
To see these additional updates run: apt list --upgradable

Das Dashboard parst Zahlen am Zeilenanfang und klassifiziert nach security, ESM und allgemeinen Updates. Sicherheitsupdates lösen einen gelben Alert aus.

Snap — Snapd-Socket

GET /v2/find?select=refresh liefert die verfügbaren Snap-Updates. Nur die Anzahl und die Package-Namen werden angezeigt.

Homebrew — data/brew-outdated.json

Wird vom Cron-Skript scripts/brew-updates.sh täglich erzeugt (06:00 Uhr). Format: { formulae: [...], casks: [...], timestamp } entspricht dem Output von brew outdated --json=v2.

Felder pro Package: name, installed (installierte Version), current (aktuellste verfügbare), pinned.

4. Claude / NanoClaw-Metriken

Rate-Limit-Fenster

Das Dashboard berechnet den Token-Verbrauch selbst durch Scannen der JSONL-Konversationsdateien — unabhängig von der Claude-API. So sind die Werte immer aktuell, ohne zusätzliche API-Aufrufe.

Datenquellen

QuellePfad
NanoClaw Agenten-Sessionsdata/v2-sessions/ag-*/‍.claude-shared/projects/-workspace-agent/*.jsonl
Claude Code CLI-Sessions~/.claude/projects/**/*.jsonl (gemountet als /host/claude-projects)

Nur Dateien, die innerhalb der letzten 7 Tage modifiziert wurden, werden gescannt (Cutoff via statSync.mtimeMs).

JSONL-Eventstruktur

{
  "type": "assistant",
  "timestamp": "2026-05-03T08:00:00.000Z",
  "message": {
    "model": "claude-sonnet-4-6",
    "usage": {
      "input_tokens": 1234,
      "output_tokens": 567,
      "cache_read_input_tokens": 8900,
      "cache_creation_input_tokens": 450
    }
  }
}

Es werden ausschließlich Events mit type: "assistant" und einem usage-Objekt ausgewertet.

Berechnete Zeitfenster

FensterBerechnungNutzen
5h rolling Summe aller output_tokens der letzten 5 Stunden. resetInMs = Zeit bis der älteste Token das Fenster verlässt. Erkennen der kurzfristigen Rate-Limit-Nähe bei Claude Max (5h-Fenster).
Heute (UTC) Summe ab UTC-Mitternacht des aktuellen Tages. Tagesverbrauch im Vergleich zum 7-Tage-Durchschnitt.
7 Tage Summe der letzten 168 Stunden. Wochenverbrauch, Trend.

Kontextmetriken

  • peak5h — Maximales 5h-Fenster der letzten 7 Tage, berechnet via Sliding-Window über sortierte Events. Wird als Referenzbalken gezeigt, wenn kein Limit konfiguriert ist.
  • dailyAvg — out7d / Anzahl aktiver UTC-Tage. Aktiver Tag = mindestens ein Assistant-Event.
  • activeDays — Anzahl Tage mit Aktivität im 7-Tage-Fenster.

Extra-Usage-Erkennung

Claude Code schreibt bei „out of extra usage"-Ereignissen synthetische Nachrichten mit model: "<synthetic>" in die JSONL-Dateien. Der Text enthält einen Reset-Zeitpunkt wie "resets 7pm". Das Dashboard:

  1. Findet den neuesten solchen Eintrag
  2. Parst die Reset-Zeit (am/pm) und sucht minutenweise den nächsten Berlin-Zeitzonenwert nach dem Hit-Zeitstempel
  3. Zeigt einen roten Alert bis der Reset-Zeitpunkt überschritten wurde

Limit-Konfiguration

Zwei Wege, Limits zu setzen — explizite env-Variablen haben Vorrang:

# Option A — explizite Token-Limits
CLAUDE_5H_OUTPUT_LIMIT=50000     # Max Output-Tokens pro 5h
CLAUDE_DAILY_OUTPUT_LIMIT=200000 # Max Output-Tokens pro Tag
CLAUDE_WEEKLY_OUTPUT_LIMIT=800000# Max Output-Tokens pro 7 Tage

# Option B — Subscription-Plan (setzt nur das 5h-Limit)
CLAUDE_PLAN=max5x                # pro | max5x | max20x

Plan-Tabelle (Output-Tokens pro 5h-Block, Quelle: Maciek-roboblog/Claude-Code-Usage-Monitor):

Plan5h-Limit
pro19.000
max5x88.000
max20x220.000

Ohne Limit-Konfiguration zeigen die Balken Vergleiche zum historischen Peak statt Absolutwerten.

Burn-Rate (60-min-Sliding-Window)

Tokens-pro-Minute über die letzten 60 Minuten — Quelle: Maciek-roboblog/Claude-Code-Usage-Monitor.

burnPerMin = Σ output_tokens(letzte 60 min) / 60
burnPerHour = burnPerMin × 60

Anders als die kumulativen 5h/24h/7d-Werte ist die Burn-Rate ein kurzfristiger Indikator. Sie ist 0, wenn in den letzten 60 Minuten keine Aktivität stattfand.

Nützlich für

Erkennen akuter Verbrauchsspitzen (z. B. eine längere Refactoring-Session). Basis für alle Forecasts.

5h-Block-Detection (Gap-basiert)

Analog zu Claude Code's nativen 5h-Sessions wird der aktuelle Block durch Rückwärts-Iteration über die sortierten Events ermittelt — sobald die Lücke zwischen zwei Events mehr als 5 h beträgt, beginnt ein neuer Block.

events.sort(byTimestamp);
blockStart = letztes Event;
für i = letztes…erstes:
    wenn (blockStart - event[i].ts) > 5h: BREAK
    blockStart = event[i].ts
    blockTokens += event[i].outputTokens
blockEndTs = blockStart + 5h

Liefert window5h.blockStart und window5h.blockEndTs — Grundlage für Time-Pacing und Projection.

Forecast — Projected & ETA bis Limit

projected5h = blockTokens + burnPerMin × blockRemainingMs / 60.000
etaToLimitMs = max(0, (limit - aktuell) / burnPerMin) × 60.000

Projected = Hochrechnung: was wird der 5h-Block-Verbrauch am Ende des Fensters sein, wenn die aktuelle Burn-Rate konstant bleibt?

ETA = Zeit bis zum Erreichen des konfigurierten Limits bei aktueller Burn-Rate. Wird in 5h, 24h und 7d separat berechnet.

Edge-Cases:

  • burnPerMin = 0 → ETA = null, im UI als „—" dargestellt
  • Kein Limit konfiguriert → ETA-Zeile entfällt
  • UI-Farbcode für ETA: rot < 30 min, gelb < 2 h, sonst grün

Time-Pacing-Warnung

Idee aus jens-duttke/usage-monitor-for-claude. Vergleicht den prozentualen Limit-Verbrauch mit dem prozentualen Zeit-Verbrauch im 5h-Block:

timePct = (now - blockStart) / 5h × 100
usagePct = out5h / limit5h × 100
pacingWarn = (timePct ≥ 10) AND (usagePct > timePct + 10)

Im UI wird ein dünner vertikaler Marker bei timePct auf den 5h-Balken gezeichnet. Bei pacingWarn = true wird der Balken-Hintergrund leicht gelb getönt und ein „⚠ Verbrauch läuft Zeit voraus"-Hinweis angezeigt.

Suppression: Erst ab 10 % Block-Zeit aktiv — bei frischen Blöcken ist die Pacing-Berechnung statistisch unzuverlässig.

Nützlich für

Frühwarnung, ohne ein hartes Limit zu kennen. Beantwortet die Frage: „Wenn ich so weitermache, schaffe ich es bis zum Block-Ende?"

Exhaustion-Learning — adaptives Limit

Das Dashboard lernt automatisch das echte effektive 5h-Limit aus vergangenen Erschöpfungsereignissen. Jedesmal wenn Claude Code die Nachricht „You're out of extra usage" in einer JSONL-Datei hinterlässt, wird der 5h-Token-Stand zu diesem Zeitpunkt rückwirkend berechnet und in data/claude-exhaustion-events.jsonl gespeichert:

out5hAtHit = Σ outputTokens für alle JSONL-Events mit:
  0 ≤ (lastExtraHitTs - eventTs) ≤ 5h

Der Median aller gespeicherten out5hAtHit-Werte ergibt das gelernte Limit. Der Median ist robuster gegen Ausreißer (z. B. ungewöhnlich kurze Sitzungen) als der Durchschnitt.

Limit-Vorrang:

dynLimit5h = CLAUDE_5H_OUTPUT_LIMIT  // explizite env → höchste Priorität
          || learnedLimit5h           // gelernter Realwert
          || CLAUDE_PLAN-Tabelle      // Plan-Schätzwert (pro / max5x / max20x)
          || 0                        // kein Limit bekannt

Das gelernte Limit hat bewusst Vorrang vor der statischen Plan-Tabelle, weil es echte Messwerte repräsentiert und das tatsächliche Extra-Usage-Kontingent einschließt — nicht nur das Basis-Plan-Limit.

API-Felder:

rate_limits.learned.limit5h    // Median-Limit in Tokens
rate_limits.learned.dynLimit5h // tatsächlich verwendetes Limit (inkl. Vorrang-Logik)
rate_limits.learned.eventCount // Anzahl gespeicherter Erschöpfungsereignisse
rate_limits.learned.events     // letzte 5 Ereignisse: [{ts, out5hAtHit}]

Datei: data/claude-exhaustion-events.jsonl — jede Zeile ein JSON-Objekt mit ts, out5hAtHit, burnPerMin, resetTs. Append-only, persistiert über Container-Neustarts.

Edge-Cases:

  • Noch kein Ereignis → learnedLimit5h = null, Fallback auf Plan-Tabelle oder kein Limit
  • Ereignis älter als 7 Tage → nicht mehr in events7d, daher kein neues Logging möglich; ältere Events in der Datei fließen aber weiter in den Median ein
  • UI-Badge „Gelernt: ~Xk · N× · aktiv/durch Limit-Env überschrieben" erscheint sobald ≥ 1 Ereignis vorliegt

Token-Metriken

Quelle

Dieselben JSONL-Dateien wie die Rate-Limit-Metriken, aber mit einem längeren Cutoff von 30 Tagen.

Pro-Session-Berechnung (summariseSession())

FeldBerechnung
totalInput/Output/CacheRead/CacheCreateSumme über alle Turns der Session
contextTokenslast.input + last.cacheRead + last.cacheCreate — das Kontextfenster des letzten Turns
contextPctcontextTokens / 165.000 × 100 — Auslastung des Auto-Compact-Schwellenwerts
contextFillcontextTokens / 200.000 × 100 — Auslastung des vollen Kontextfensters
cacheHitPctcacheRead / (input + cacheRead + cacheCreate) × 100
turnsAnzahl Assistant-Events in der Datei

Nützlich für

  • Cache Hit Rate — Hohe Werte (≥ 60 %) bedeuten, dass Prompt-Caching effektiv funktioniert und weniger Token abgerechnet werden.
  • Context % — Bei Annäherung an 100 % des Compact-Schwellenwerts (165k) wird Claude Code das Gespräch automatisch komprimieren. Das ist eine gute Prüfung, ob eine Agent-Session sich endlos aufbläht.
  • Output Tokens — Gibt an, wie viel eine Agent-Session tatsächlich produziert hat (maßgeblich für Rate-Limits).

Log-Metriken

Quelle

logs/nanoclaw.error.log — letzte 8.000 Zeilen via tail -n 8000.

Level-Klassifizierung

Jede Zeile wird via Regex klassifiziert (nach Entfernung von ANSI-Escape-Codes):

fatal  → / FATAL | \[FATAL\]/
error  → / ERROR | \[ERROR\]/
warn   → / WARN  | \[WARN\]/

Zeilen ohne Match (Info, Debug, etc.) werden für die Metrik ignoriert.

Zeitstempel-Rekonstruktion

Log-Zeilen haben keine Datum-Information, nur Uhrzeit: [HH:MM:SS.mmm]. Um absolute Zeitstempel für die 24h-Verteilung zu berechnen, geht die Funktion rückwärts durch die Zeilen und erkennt Mitternachtsübergänge (wenn tod von einer Zeile zur nächsten um mehr als 1h steigt, wurde Mitternacht überschritten).

Ausgabe

6. Dashboard-Tabs

Overview

Alert-Banner (alle kritischen Zustände), Stat-Cards (Zusammenfassung), Log-Aktivitätschart (24h), Container-Tabelle, Agent-Groups-Tabelle.

System

CPU/RAM/Disk/Load-Cards, CPU-Kern-Grid, Memory-Detail, Disk-Nutzung, Disk-I/O, Netzwerk-Interfaces, Paket-Updates, OS-Info, Docker-Daemon-Info, Tailscale Self + Peer-Liste, Docker Volumes + Networks + Images.

Agents

Pro Agent Group: Wiring-Konfiguration (Channel-Typ, Platform-ID, Session-Mode), Session-Status, Heartbeat, Context-Auslastungsbalken, Token-Statistiken.

Tokens

Rate-Limit-Fenster (5h/24h/7d mit Balken und Reset-Timer), Summary-Cards (Gesamt-Tokens, Cache Hit Rate), Tabelle aller CLI-Sessions (letzten 30 Tage) mit Context-% und Cache-Hit-Balken.

Sessions

Pro Session: Inbound/Outbound-Nachrichten-Tabellen, Processing-Acks, Session-State, Heartbeat-Status, Message-Metriken (Median-Antwortzeit, Stundenverteilung).

Channels

Alle Messaging-Groups mit Channel-Typ, Platform-ID, Unknown-Sender-Policy. Zeigt welche Agent-Groups an welche Channels verdrahtet sind.

Users

Alle registrierten Nutzer mit ID, Kind, Display-Name, Rollen (owner/admin global oder scoped) und Erstellungsdatum.

Messages

Session-Picker → zeigt vollständige Inbound/Outbound-Nachrichtenhistorie einer Session. Content wird aus JSON-Payloads geparst und leserlich dargestellt.

Logs

Live-Stream via SSE aus nanoclaw.log + nanoclaw.error.log. Level-Filter (debug/info/warn/error), Auto-Scroll, Initial-History (letzte 500 Zeilen). Log-Zeilen werden farblich nach Level hervorgehoben.
